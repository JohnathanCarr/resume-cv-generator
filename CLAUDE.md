# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A Chrome extension (MV3, no build step) that generates tailored resumes and cover letters from a saved profile and a pasted job description by calling the OpenAI API directly with the user's own key. Users seed their profile by uploading their existing resume PDF, which is parsed entirely in the browser with no LLM call. Nothing runs outside the browser.

## Commands

There is no bundler, linter, or test runner. Files in `extension/` are loaded straight from disk.

```bash
# Syntax-check without running
node --check extension/app.js extension/print.js
node --input-type=module -e "import('./extension/generation/pipeline.js').then(m => console.log(Object.keys(m)))"

# Unit tests for the pure generation helpers (no API calls)
node --test 'test/unit/*.test.mjs'

# Smoke test: the real app.html in headless Chrome over a stubbed chrome API and
# stubbed OpenAI; clicks through both generation flows, the keyword dialog,
# downloads, failure + Retry, Settings, theme and tour, and checks the tailored
# resume's page height against test/smoke/expected.json. Run before every PR.
./scripts/smoke.sh            # --update records a new height after an intended layout change

# Prompt evals (in-process, no server; ~$1 for the full set, key from OPENAI_API_KEY or test/eval/.env)
node test/eval/run.js --profiles david --jobs 02   # one pair
node test/eval/run.js --label my-change --baseline # full set, summary copied to test/eval/baselines/

# Extension: chrome://extensions → Developer mode → Load unpacked → select extension/
# After editing app.js/manifest.json click ↻ on the extension card; app.html/styles.css only need a tab refresh.

# Store upload zip → dist/resume-studio-<version>.zip (version read from the manifest)
./scripts/package.sh
# Store screenshots (1280×800) from the harness in store/, needs the :8790 static server running
./scripts/screenshots.sh

# Parser harness (exercise resumeParser.js against fixtures without the extension)
python3 -m http.server 8790      # from repo root
# open http://localhost:8790/test/parser.html — pick a fixture or upload any PDF
```

Regenerate a synthetic fixture PDF from its HTML source with headless Chrome:

```bash
"/Applications/Google Chrome.app/Contents/MacOS/Google Chrome" --headless=new --disable-gpu --no-pdf-header-footer \
  --print-to-pdf="$PWD/test/fixtures/<name>.pdf" "file://$PWD/test/fixtures/<name>.html"
```

Real resumes for regression testing go in `test/fixtures/local/` (gitignored). Never commit a PDF with real contact details.

## Architecture

```
extension/app.html ──► extension/app.js (CoverLetterApp) ──► chrome.storage.local
        │                     │  ├─ resumeParser.js  (PDF → profile, pure functions, pdf.js)
        │                     │  ├─ profileMerge.js  (additive dedup merge)
        │                     │  ├─ generationFlow.js (runGeneration + COVER_LETTER / RESUME: the shared generate flow)
        │                     │  ├─ preview/         (resumeHtml / coverLetterHtml: pure HTML; measure: one-page layout; export: PDFs + file names)
        │                     │  └─ generation/      (ES modules, lazily imported)
        │                     │       ├─ pipeline.js  ──► openai.js (fetch) ──► api.openai.com
        │                     │       └─ matchAnalysis / keywords / companyResearch / tailor + layout + baseline + highlight / coverLetter / config
        │                     └─ chrome.storage.session.printJob ──► extension/print.html (window.print → Save as PDF)
        └─ extension/styles.css (25 numbered sections; fonts and tokens in Section 1)
```

**Script loading.** `app.html` loads the bundled libraries (`jspdf.min.js`, `pdf.min.js`, globals `window.jspdf` and `pdfjsLib`) and `theme.js` as plain scripts, then `app.js` as the page's one ES module (`<script type="module">`). `app.js` imports `resumeParser.js` (`ResumeParser`), `profileMerge.js` (`ProfileMerge`), `onboarding.js` (`OnboardingTour`) and `progress.js` (`GenerationProgress`); none of them sets a global. `theme.js` stays a plain script on purpose: it shares nothing, and running during page load sets the theme before first paint. Modules are strict mode. `test/parser.html` imports `ResumeParser` the same way.

**Generation flow (`extension/generationFlow.js`).** `generateCoverLetter()` and `generateResume()` in `app.js` are one line each: `runGeneration(this, COVER_LETTER | RESUME)`. The runner owns what both share, in this order: posting and name checks, the kind's own input check (`missingInput`, the resume's "upload first"), the API key, `showLoading()`, a step timer, the kind's `prepare` (the resume's baseline), `checkKeywords()` (the ATS gate, cancel → `progress.hide()` and "Cancelled."), the kind's `generate(run, checked)`, then status, `progress.done()`, `recordFirstGeneration()` and the download button; on error `progress.fail()`, `showError(errorPrefix + message, Retry)` and `failedStatus`; always `hideLoading()` and the `[timing]` line. A kind holds only what differs (labels, button id, retry, steps). The runner calls the app for UI and state, never the DOM beyond the posting textarea and the download button. Unit-tested over a fake app in `test/unit/generationFlow.test.mjs`.

**Data model.** `profile` lives in `chrome.storage.local` and is the single source of truth: `name, contact (multi-line text), location, summary, education[], skills[], experiences[], projects[], extras[]`. Entry arrays carry `id` and (experiences/projects) `mustInclude`. `extras[].type` is one of `CoverLetterApp.EXTRA_TYPES`. `uploadedResume` (base64 PDF + metadata) is stored under its own storage key so profile saves stay small. `baselineResume` is the frozen snapshot of the uploaded resume as parsed (`generation/baseline.js`: `{ version, source, createdAt, resume }` with positional ids `exp:1`, `proj:2`, `edu:1`, `extra:3`); generation edits it, only a new upload replaces it, and profile edits never touch it. `ensureBaseline()` re-parses the stored PDF when the snapshot is missing or its `version` is older than `BASELINE_VERSION` (bump that when the parser or snapshot shape changes). Other keys: `lastResume` (`{ resumeContent, tailored, changes, coverage, jobText, company, role, generatedAt }`, restored into the preview on load only). `education` was a single object before multi-entry support; `migrateEducation()` in `loadData()` converts legacy saves.

**Repeated UI is built in JS, not HTML.** Static sections live in `app.html`; every per-item card (education, experience, project, extras, skill tag) is a template string in `createXElement()` in `app.js`. If a card looks wrong, the markup is there, not in `app.html`.

**Upload → autofill flow.** `handleResumeUpload()` validates and stores the PDF, then `autofillFromResume()` runs `ResumeParser.parse()` and `ProfileMerge.merge()`. Merge is additive: new items appended, matching items (normalised keys: institution+degree, company+title, project name, title+organisation) enriched by filling blanks and unioning bullets; ids and `mustInclude` are preserved; scalars are never overwritten. Re-uploading the same resume is a no-op. Parser warnings surface in `#profile-status` (the Profile tab has its own status element; `#generation-status` is in the Generate tab).

**Resume parser (`resumeParser.js`).** Stages: positioned lines from pdf.js → body font size + section split via `SECTION_SYNONYMS` dictionary → per-section parsers. Non-obvious facts it depends on:
- `page.commonObjs` (font names → bold/italic) is empty until `page.getOperatorList()` has run.
- CSS list markers are **not** in the PDF text stream; bullets are detected by indent (x > left margin) or an explicit glyph. Wrapped lines are re-joined using pdf.js `hasEOL` when the generator emits it, otherwise by right-margin proximity.
- Unknown all-caps bold headings become kind `unknown`; `looksLikeEntryList()` decides whether to file them as extras of type `other` or skip with a warning. Add new heading variants to `SECTION_SYNONYMS` rather than widening the fallback.
- Skills sections are either lists or prose; `parseSkills()` joins wrapped bullets first, then in prose mode keeps only fragments that pass `looksLikeSkill()` (capitalised/acronym, single token with `./+/#/-`, or in `KNOWN_SKILLS`).

**Generation.** `extension/generation/` is plain ES modules with no Node or DOM dependency, so the same files run in the extension page and under Node for evals. `app.js` reaches them through `this.generation()`, a cached dynamic `import()`, so they load only when first needed. `openai.js` is a fetch wrapper with the SDK's call shape (`chat.completions.create`, `responses.create`); there is no `openai` npm dependency anywhere. Prompts are string interpolation (`formatEducation()` / `formatExtras()` helpers in `profileText.js`) against the model pinned in `generation/config.js`. The extension renders resume JSON in `formatResume(content, profile)` (`preview/resumeHtml.js`, pure, unit-tested in `test/unit/preview.test.mjs`) with **inline styles and hardcoded pt sizes** because the same `.resume-page` markup is copied into `print.html`, which does not load `styles.css`; resume output styling is edited in `formatResume()`, page geometry (`@page`, margins) in `print.html`. **Preview and downloads (`extension/preview/`).** `resumeHtml.js` (`escapeHTML`, `escapeResume`, `formatResume`, `formatContactLine`, `formatSkills`) and `coverLetterHtml.js` (`formatCoverLetter(text, profile, date)`) are pure and run under Node; `measure.js` (`PAGE_PX`, `measureResumeHeight`, `measureLayout`) renders off-screen in `<body>`, so body must stay at 16px; `export.js` holds `sanitizeFilename`/`suggestFilename`, `buildCoverLetterPdf` (jsPDF from the preview's `.letter-body`), `saveBlob` (chrome.downloads, link fallback) and `printableResumePage`/`openResumePrintView`. `app.js` keeps the UI around them (`renderResumePreview`, `promptForFilename`, status messages). `downloadResumePDF()` stores the markup in `chrome.storage.session` and opens `print.html`, whose `print.js` consumes it once, sets `document.title` (Chrome's proposed filename) and calls `window.print()`. `formatResume()` takes text that is already HTML-escaped: `highlight.js` output for tailored resumes, `escapeResume()` for raw data (page measurement, older `lastResume` entries without a `tailored` document); it escapes the profile's name and contact line itself. Every other template that reaches `innerHTML` (profile cards, cover letter) runs user and model text through `escapeHTML()`, and skill tags are built with DOM nodes. Treat model output as untrusted: a pasted posting can steer it.

**Styling.** Flat "teal leads" design (mockups in `design/mockups/`): 2px solid borders, square corners, hard offset shadows, no blur or gradients. `styles.css` Section 1 loads the bundled fonts (`extension/fonts/`, Fraunces 500 for headings, Space Grotesk for body; SIL OFL, licenses alongside) and defines the palette and light/dark tokens (`[data-theme="dark"]`). The palette is locked; teal, green and brick are too light as *text* in light mode, so text uses `--primary-text`, `--success-text` and `--danger-text` (4.5:1 on ivory and beige) while fills and borders use `--primary`, `--success` and `--danger`. The resume and cover-letter paper is always white with black serif text. Section 25 honours `prefers-reduced-motion`, and `theme.js` checks `reducedMotion()` before its JS animations. **Generation progress**: `progress.js` (`GenerationProgress`) drives the `#gen-progress` strip above the job description and preview; `app.js` calls `progress.start()` in `showLoading()`; `generationFlow.js` calls `mark()` before each pipeline step, `pause()`/`resume()` around the keyword dialog, and ends each run with `done()`, `fail()` or `hide()` (cancelled). Dialogs and the tour manage focus (see `openModal()`, `setPageInert()`; generation makes everything but the progress strip inert); status text also goes to the `#sr-status` live region via `announce()`. Form controls (`input`, `textarea`, `select`) do not inherit `color` or `font-family` — any rule that themes a control's background must also set those, or it renders Chrome's black-on-monospace defaults in dark mode. The four "+ Add ___" buttons are the only `.btn-secondary` that are direct children of `.section`; target them with `.section > .btn-secondary`.

## Conventions

- Conventional Commits, small focused commits on a feature branch, one PR per phase. Scopes in use: `profile`, `parser`, `generation`, `extension`, `onboarding`, `settings`, `prompts`, `eval`, `docs`. CSS that changes what users see is `fix`, not `style`.
- Merge PRs with "Create a merge commit" or "Rebase and merge" so individual commits stay in history.
- The project directory path contains a colon (`RS:CV_Generator`), which breaks `npx`; run any CLI via `node node_modules/...` instead.
- `.claude/launch.json` (the `extension-static` preview server on :8790) lives in the parent folder, outside this repo; edit it in place, it cannot be committed.

## Background worker and permissions

`background.js` opens the app tab on install and on toolbar click, focusing an existing one instead of opening a second. It does this **without the `tabs` permission**: `app.js` `connectToBackground()` holds a `chrome.runtime.connect({ name: 'app' })` port while the page is open, the worker reads the tab id from `port.sender.tab` and keeps it in `chrome.storage.session` (the worker is unloaded when idle and would forget it), and the port closing clears it. The page reconnects when the worker restarts and stops once `chrome.runtime.id` is gone (extension reloaded/removed). Manifest permissions are exactly `storage`, `unlimitedStorage` (uploaded PDF can exceed the 10 MB quota), `downloads` (cover letter PDF) and the `api.openai.com` host; each has a justification in `store/listing.md` and `PRIVACY.md` — keep all three in step if a permission changes.

## Onboarding

First run is detected two ways: `chrome.runtime.onInstalled` (reason `install`) in `background.js` opens the app tab and seeds `onboarding` in `chrome.storage.local`; `app.js` `init()` treats a missing/false `onboarding.seen` as first run and starts the tour. Dev reloads of an unpacked extension do not fire `onInstalled`; reset by deleting the `onboarding` storage key or use the header "?" button, which replays the tour on demand. The tour (`extension/onboarding.js`) is a spotlight + tooltip sequence over real elements, switching tabs and scrolling as it goes; Skip and Escape always exit. The Getting Started checklist card on the Profile tab ticks itself from live state (resume uploaded, name set, key saved, first document generated; the key line shows OpenAI's verification result) and hides when complete.

## Generation pipeline (current)

Key handling: the extension stores the OpenAI key in `chrome.storage.local` (`apiKey`; masked in Settings, replace-only) and passes it to the pipeline functions, which send it as `Authorization: Bearer` to `api.openai.com` only (the manifest's sole host permission). `createClient(apiKey)` builds a per-call client and `safeErrorMessage` scrubs key-shaped strings from errors; `verifyKey()` makes one tiny call so Settings can show Verified. Errors carry `.status` (401 = rejected key) and `.code` (`timeout`, `network`, `output_truncated`).

Model: one pinned model in `extension/generation/config.js` (`gpt-5.6-terra`; verification uses `gpt-5.6-luna`). GPT-5 models reject `temperature`/`max_tokens` — use `reasoning_effort` and `max_completion_tokens`. All generation goes through `generateStructured()` with strict `json_schema` output; a `finish_reason: length` is surfaced as an error.

Per document, in `extension/generation/` (orchestrated by `pipeline.js`):
1. `matchAnalysis.js` — reads the posting against the profile (rendered with stable ids `exp:3`, `proj:5`, `edu:1`, `extra:6`, `skill:Go`) and returns company, role, seniority, `about_company` (posting-only), every requirement with supporting ids and strength (strong/partial/none), and the posting's exact ATS keywords. Replaces the old regexes, which had reported companies like "a Analyst" and "ions". Returned as `matchAnalysis`; the extension keeps it on `lastMatchAnalysis` for the deferred Match panel. The extension runs this step on its own first (`analyzeJob()`) and passes the result back as `match`, so the gate below does not pay for the analysis twice.
   - **ATS keyword gate** (`keywords.js`, pure; `generationFlow.js` `checkKeywords()`). The match analysis marks each keyword `core` (a concrete, nameable skill/tool/certification a recruiter would filter on, in a required qualification or repeated) or `supporting` (job title, experience descriptions, categories, nice-to-haves, soft skills); `keywordTerms()` reads either that shape or legacy plain strings (treated as core). `missingKeywords()` whole-term-matches the **core** keywords against everything in the profile (skills, bullets, coursework, extras…) and returns the ones found nowhere, at most `MAX_ASKED` (8), in posting order. Supporting keywords are never asked about but are still passed to the generators for mirroring. The extension shows them as checkboxes; `applyKeywords()` appends the ticked ones to `profile.skills` (saved — the profile stays the only source of truth, so the no-fabrication rules hold) and patches the match (`skill:<term>` evidence on requirements that name the term, none→partial). Unticked terms are simply skipped; nothing is remembered between postings (the old `ignoredKeywords` "don't ask again" list was removed, and its storage key is cleared on load). Cancel aborts generation.
2. `companyResearch.js` (cover letters, when `research` is on) — Responses API with the hosted `web_search` tool, at most `RESEARCH.maxSearches` searches at `low` context; produces a brief (what they build / care about / current priorities / context) with a URL per fact, or `found:false` and a note. The extension caches briefs per company for 30 days in `companyBriefs` and sends the cache as `briefCache`; only briefs from real research are cached or reused (`isResearchedBrief()`: `source: 'research'`, or for older briefs, any with searches or token usage), so a posting-only brief never blocks research. Each search bills a tool call plus ~13K input tokens; research roughly quadruples a cover letter's cost.
3. `tailor.js` — **resumes are tailored as an edit list, never rewritten.** Generating a resume requires an uploaded resume; `pipeline.js` `tailorResume()` edits the baseline snapshot (`baselineResume.resume`), so every posting starts from the user's own resume. The model sees the resume with line ids (`summary`, `skills:2`, `exp:1.b3`, `proj:2`, `edu:1.coursework`, `extra:4`) and a **pool** of profile material that is not on the resume (`buildPool()`: unused bullets of the same job/project `more:exp:1.2`, other projects `pool:proj:3`, other extras `pool:extra:1`, profile skills not on the resume, including keywords just confirmed in the gate, and other courses). It returns `edits[]` of four ops: `rewrite` (one line, posting's terms), `swap` (bullet ↔ unused bullet of the same job/project, project ↔ project, extra ↔ extra), `skills` (a skill line's full reordered item list) and `remove` (only to fit the page, below). Jobs, education entries and headers are never editable. `validateEdits()` enforces it in code: target exists and is edited once, pool items used once, same-kind/same-owner swaps, no number not in the source line, **no named term dropped** (any word with a capital, digit or `+#./`, first word excepted), length ≤ 1.4× + 4 words, skills keep every original item and add only profile skills, coursework only from profile courses, no edits inside a swapped-out project. Invalid edits go back for up to two repair passes; any still invalid are dropped (`metadata.rejected`). `applyEdits()` returns the tailored document (same shape and ids as the baseline) and `changes[]` (`{ id, op, before, after, added?, reason }`) for the preview highlights; `resumeDocToSchema()` (baseline.js) converts either document to the shape `formatResume()` renders (skill lines keep the resume's own labels; a project's header text follows its name). `metadata.coverage` is core-keyword coverage before → after; `metadata.page` is `{ usedPx, afterPx, limitPx, fits, trimmed, undone, estimated }`. Summary: editable only if the upload has one, so none is ever added.
   - **One page, hard limit, planned up front** (`layout.js`, pure). Before generating, `preview/measure.js` `measureLayout()` renders the uploaded resume off-screen at print width (`min-height` dropped) and records its height plus, per line kind tagged `data-kind` in `formatResume()` (`bullet`, `summary`, `skills`, `coursework`, `extra`, `projectHeader`), the font, usable width, line height and gap, with a canvas `textWidth()`. `lineCount()` wraps text the way the browser does (it matched every rendered line on the fixture). The prompt tags each line with its size and spare characters (`[exp:1.b2 · 2 lines, 14 spare]`) and states the page's free lines, or how many must be cut; a fourth op, `remove` (bullet, project, extra or coursework line; every job keeps a bullet), exists only to fit the page. `validateEdits()` totals every edit's height (`editDelta()`) and adds a `PAGE:` error when the result would pass the limit (one page less half a line); up to two repair passes; `fitToPage()` is the last resort (undo growth edits, largest first, then remove whole items: extras, project bullets/projects, older jobs' later bullets, coursework). The extension then measures the real result and, if it still spills over, re-requests with the measured error added to `usedPx` (twice at most). Under Node (evals) `makeLayout({})` estimates the same CSS; the estimate runs ~5% tall.
   - **Preview highlights** (`highlight.js`, pure). `previewResumes(tailored, changes)` returns `{ marked, clean }` in `formatResume()`'s shape: `marked` wraps each change in `<span class="rs-added">` (rewrites: only the inserted words, by a word-level LCS diff that ignores surrounding punctuation; skills: added items, or the new part of a respelling like "PostgreSQL (Postgres)"; swaps: the whole line or project, `rs-line`; removals: absent), with a `title` giving the old text and the reason. `app.js` `renderResumePreview()` shows `marked`, keeps `formatResume(clean)` as `lastCleanResumeHTML`, and `downloadResumePDF()` prints that, so highlights never reach the PDF. The compare bar above the preview (`#resume-compare-bar`) has the Tailored / Original toggle (`showResumeView()`; Original draws the uploaded PDF's pages with pdf.js once per upload) and the core-keyword coverage chip. `formatSkillsComprehensive()` splits a skill line at its first colon only, because highlight titles contain colons. Highlight colours are fixed in styles.css Section 24 (the page is white in both themes).
   - **Bullet ids after edits.** Tailored entries carry `bulletIds` (the baseline id of each remaining bullet; swapped-in projects get `proj:N.newK`) so the preview can match lines to `changes` after removals.
   - **Parser skill groups.** `parseSkills()` returns `{ skills, groups }`; groups keep the resume's category labels (`Languages: …`). The snapshot stores them as `skillGroups` (`BASELINE_VERSION` 2; older snapshots are re-parsed on load).
4. `coverLetter.js` — hard rules (nothing about the candidate outside the profile, nothing about the company outside the brief/posting, partial matches described as such, never refer to the profile as a document), two exemplar paragraphs for voice, ~300 words in 3–4 paragraphs, and a `claims[]` output where every claim names its source; `unsourcedClaims()` validates, `pipeline.js` does one repair pass, and any remaining unsourced claims are returned and shown in the status line.

**Timing.** `generation/timing.js` (`createTimer()`, `formatTimings()`) records each step of a run. The pipeline returns its own steps in `metadata.timings` (`analyze`, `request`, `repair N`; `research`, `letter`, `repair`); `generationFlow.js` wraps the outer steps with `run.timed()` (read posting, keyword check (you), load resume, measure layout, tailor, measure page, refit N, render preview, cover letter), attaches the pipeline's breakdown with `run.detail()`, and its `reportTiming()` prints one `[timing]` console line per run and stores it on `lastApiCall.timings` for Save logs.

Evals: `test/eval/` (see its README). Run before and after any prompt change (current baselines: `2026-10-02-one-page.json` for resumes, `2026-09-20-in-extension.json` for cover letters). `test/unit/pipeline.test.mjs` runs the cover-letter pipeline over a stubbed `fetch`; `--rescore` re-applies a changed rubric to saved outputs without API calls. Baselines in `test/eval/baselines/`. Known rubric limits: it cannot check whether company facts are true, and `pageFill` is relative to the profile's material, so thin profiles score full marks for short resumes.

**Truncation.** At a 4000-token cap about 1 in 15 cover letters failed with `output_truncated` (the model spent the cap reasoning before writing). The cap is now 6000, like the resume, and `retryTruncated()` in `pipeline.js` repeats any tailoring or cover-letter call once on that code. If the cover letter's repair pass still fails, the first draft is returned with its unsourced claims flagged (`metadata.repairFailed`).

## Status and roadmap

The extension became standalone on 2026-09-20 in three PRs: #6 `generation-in-extension` (OpenAI calls moved from the proxy into `extension/generation/`, evals in-process), #7 `resume-pdf-client-side` (Puppeteer replaced by `print.html` + `window.print()`), #8 `remove-proxy` (server, setup scripts and old deploy docs deleted; README/Quick Start rewritten). Nothing runs outside the browser; `https://api.openai.com/*` is the only host permission.

Phase 4 `web-store-release` (2026-09-21) made it submittable: manifest at `1.0.0` with a real description, icons and only the permissions it uses; `tabs` removed via the port scheme above; `PRIVACY.md`; `scripts/package.sh`; `store/` with listing copy (`listing.md` is the source for every dashboard field), the icon (`icon.svg`, rendered to `extension/icons/` with headless Chrome) and three screenshots from a harness that runs the real `app.html` over a stubbed `chrome` API (`store/screenshots.html`, fictional eval profile). The icon is a placeholder in the app's own mark; replace `icon.svg`, re-render, and re-upload when there is a real one.

**Store history.** 1.0.0 was submitted Unlisted and **rejected** (2026-09-30, "Blue Argon": remotely hosted code). The scanner matched the cdnjs PDFObject URL inside the bundled `jspdf.min.js`, in an output mode the extension never uses; #12 removed it and `package.sh` now refuses to build if `extension/` contains a remote script URL. 1.1.0 (2026-10-06) ships the tailoring redesign (#13–#15, below) plus the file-name prompt, and is the next submission.

**Resume tailoring redesign (#13–#15, 2026-10-01 → 10-06).** #13 baseline snapshot of the uploaded resume, upload required, summary only if the upload has one, core-only keyword gate (no "don't ask again"); #14 edit-list tailoring with the code validator and the hard one-page limit; #15 preview highlights, Tailored/Original toggle, keyword coverage chip, clean PDF. Before either download, `promptForFilename()` asks for the file name (prefilled `Name - Company - Resume|Cover Letter`; `sanitizeFilename()` strips characters no OS accepts); for the resume it becomes the print page title, which Chrome proposes as the "Save as PDF" name.

**Store process (manual):** developer account registered → the existing item (`lcacnldmjmlkcokfdafoenkpedmmdefj`) → Package → upload the new `dist/resume-studio-<version>.zip` → refresh the listing from `store/listing.md` (description and screenshots changed in 1.1.0) → visibility **Unlisted** → submit. Every version is reviewed again, and a new version cannot be uploaded while one is under review, so batch changes. Test the store install (permission prompt, `onInstalled` tour) from the unlisted link, then flip to Public. Bump `version` in the manifest for each upload.

**After that (deferred features):**
- **Listing polish.** A designed icon, more screenshots (cover letter, research citations, print view), a promo tile (440×280) if the store asks for one.
- **Keyword gate follow-ups.** Confirmed terms only ever land in `skills`; a way to attach one to a specific experience (so it appears in a bullet, not just the skills line) would help ATS scoring further. Also consider showing the *matched* keywords alongside the missing ones so the user sees the whole picture.
- **Match panel.** `matchAnalysis` is stored on `lastMatchAnalysis` but not shown. A panel beside the preview listing each requirement with ✓/◐/✗ and the profile evidence, so users fix their profile rather than the output.
- **Cover-letter latency** (~45–60s): run match analysis and company research concurrently; research only needs the company name, which a cheap first pass could extract.
- **One-click resume PDF**, if the print dialog proves annoying: `chrome.debugger` + `Page.printToPDF`. Costs a permission reviewers scrutinise and a "debugging this tab" banner, so not before the store listing is approved.
